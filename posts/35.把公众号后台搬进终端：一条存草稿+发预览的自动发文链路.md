# 把公众号后台搬进终端：一条"存草稿+发预览"的自动发文链路

前阵子搭了 [博文自动化系统](post-detail.html?id=4)，个人网站那边已经能对话出稿、一键发布了。于是顺手想：公众号能不能也这么玩？目标是让 AI 写稿、排版、存草稿，最后把**预览链接**发给我，我看完自己点发布。发布这个动作从设计上就交给人：一是公众号发文章要有人负责，必须经过人工审核；二是微信官方也不希望 AI 自动发文，群发限制每天 1 次，等于把节奏锁死在人工层面。AI 只负责到"草稿 + 预览"为止。

折腾了一天半，路线换了三次，坑踩了一地，最终跑通。把过程记下来。

## 先说结论

最终链路（2026-10-07 跑通）：

```
扫码登录(一次) → cookie+token 落盘
    ↓
写稿(Markdown) → 转内联样式 HTML
    ↓
filetransfer 传封面 → operate_appmsg sub=create 存草稿
    ↓
appmsg?action=get_temp_url → 临时预览链接(免扫码,手机直接打开)
    ↓
用户手机确认 → 手动点发布
```

全部是 Python 标准库，零第三方依赖，两个脚本共约 500 行：`mp_client.py`（check / save-draft / temp-url / del-draft）和 `wxmp_login.py`（CDP 驱动 Chrome 完成扫码登录）。

## 路线一：官方 API——卡在 IP 白名单

最正统的思路是公众号 API。个人订阅号**可以**申请 AppID/AppSecret（微信开发者那边就能办下来），这一步没问题。真正卡住的是 **IP 白名单**：官方接口要求把调用方的出口 IP 填进白名单才放行，意味着得有一个固定的公网 IP。本地开发环境换台电脑、换个网络就得重新配一遍白名单，折腾成本比收益高。对个人号"每天一篇"的用量来说不划算，这条路放弃。

## 路线二（尝试）：浏览器自动化——三个连环坑

退而求其次：让 AI 直接驱动浏览器操作公众号后台。听起来最稳，实际翻车三次：

### 坑 1：CDP 端口绑不上

Hermes 内置的 Chromium 启动后进程活着，但 remote-debugging 端口死活不 listen，日志只有一行，怎么加参数都没用。换了另一套 Chrome for Testing 二进制，1 秒起来。**同样是 Chromium 系，不同构建版本在这个沙箱环境下的 CDP 行为天差地别**——排查方向先想"换二进制"，别在参数上死磕。

### 坑 2：桌面弹了一屏关不掉的"窗口"

Chrome 反复弹 macOS 钥匙串密码框（Chromium Safe Storage，每次新拉进程弹一个），模态框杀不掉进程就一直在，桌面弹了一屏"关不掉的窗口"。截图发给我看，我以为是网页窗口——其实一个网页都没有。

解法：启动参数加 `--use-mock-keychain --password-store=basic`，用内存钥匙串，彻底不碰系统钥匙串。

### 坑 3：微信拒扫二维码截图

"把二维码截图发我，我来扫"——微信不认转存的二维码图片，提示无法识别。**登录二维码必须显示在真实屏幕上**，人回到电脑前扫。这是微信的反自动化设计，绕不过去。

浏览器路线本身能走通，但有两个结构性问题让它不如接口方案合适：

1. **浏览器要全程常驻**：AI 每一步操作（点菜单、填表单、传图）都发生在这个有头浏览器里，进程一挂流程就断；
2. **AI 操作图形界面不如直接打接口**：能做，但页面结构一变就抓瞎，元素定位、点击坐标哪一步出错都得重头来，稳定性不如命令行，也容易出错。

另外坑 3 决定了首次登录必须人在场。综合下来，浏览器全程参与，意味着链路始终系在最不稳定的一环上。我想要的是一条**浏览器只出现一次**的链路。

## 路线三（正解）：网页登录态 + 接口回放

和路线二的本质区别在**浏览器参与多久**：

- **路线二**：浏览器全程参与。发文每一步（新建、填标题、排版、传封面、存草稿）都是 AI 在网页界面上模拟点击，浏览器得一直开着；
- **路线三**：浏览器只用来完成登录这一次人机交互。扫码进后台后，把 cookie 和 token 抓下来落盘；之后所有发文动作直接回放网页后台的 HTTP 接口，浏览器关掉，AI 自己就能干活。

登录态落盘后，链路就和浏览器彻底解耦了：浏览器崩了、关掉了都不影响发文，唯一要人工参与的环节只剩登录态失效后的一次扫码。

### 登录：CDP 抓 cookie

用 CDP（Chrome DevTools Protocol）驱动一个可见的 Chrome 实例：打开 mp.weixin.qq.com → 用户对着屏幕扫码 → 轮询 URL 直到跳到后台首页（URL 里带 token）→ 从 CDP 会话抓全部 cookie，连同 token 存进一个 0600 权限的 JSON 文件。

关键点：Chrome 用**持久化 profile**，cookie 寿命是小时到天的量级，失效后重开登录页常常能免扫码直接进后台——所以维护成本远低于想象。

### 发文：三个接口

**① 传封面（filetransfer）**——踩坑最重的一个：

```
POST /cgi-bin/filetransfer?action=upload_material&f=json
     &scene=1&seq=1&ticket_id=...&ticket=...&svr_time=...
Content-Type: multipart/form-data
字段名: file          ← 不是 media,不是 upfile
不要带 groupid=0      ← 带了直接 -80018
```

- 字段名试过 `media`、`upfile` 都是 `invalid args`，只有 `file` 对；
- query 里缺 `scene=1&seq=1` 就 `-80018`；
- `groupid` 不带就行，带 `0` 也会 `-80018`——默认分组不是 id 0。

返回的 `content` 字段就是 fileid，还有现成的 `cdn_url`。

**② 存草稿（operate_appmsg）**：

```
POST /cgi-bin/operate_appmsg?sub=create
title / content(内联HTML) / fileid0(封面) / author / digest / data_seq / token
```

`data_seq` 是防并发用的随机数，自己生成即可。成功返回顶层的 `appMsgId`（注意是 camelCase，不在 data 里）。

**③ 预览（get_temp_url）**：

```
GET /cgi-bin/appmsg?action=get_temp_url&appmsgid=...
```

返回一个临时链接，**手机浏览器直接打开就能看排版效果，不需要扫预览二维码**。这一步是整条链路体验提升最大的地方——以前每次都要"电脑生成二维码 → 手机扫 → 确认"，现在链接发过去 3 秒开看。

### 一个隐蔽的坑：掉线检测误报

写 `check` 命令验证登录态时，脚本一直报"要求重新登录"，但浏览器里明明正常登录着。排查发现响应体正则里有个 `loginpage`——而**登录态正常的后台首页**导航里就包含 `/misc/pluginloginpage` 这个路径，被误匹配了。掉线判断只能认强信号（302 跳登录页、"重新登录"字样），不能用"页面里出现 login 字样"这种弱特征。

### 排版坑：深色模式下的内联样式

预览时发现正文里多处出现"白色胶囊"——行内代码的浅灰背景（`#eef1f4`）在手机深色模式下不反转，直接变成一块白色圆角块。原因是微信文章页支持深色模式，但正文内联样式用不了 CSS 变量，也没法写 media query，写死的浅色背景在深色底上必然发白。

解法：所有装饰性背景改用**半透明灰**（`rgba(127,127,127,0.12~0.18)`）。同一组内联样式在浅色模式下渲染成浅灰、深色模式下渲染成深灰，两种模式都自适应，代码行内、代码块、引用块背景统一这么处理。

## 效果

现在整个流程就是对话：

> 你：写一篇 XXX 主题的推文
> AI：（写稿 → 排版 → 存草稿 → 发预览链接）草稿已存，预览在这，看完你自己点发布

发布动作永远由人完成，AI 只负责到预览为止。

## 经验总结

1. **官方 API 拿不到的能力，网页接口回放是最省事的替代**——前提是能拿到登录态，而扫码类登录态一次扫码可以维持数天；
2. **反自动化的边界要提前摸清**：微信拒扫截图二维码、接口字段名和参考实现不一致、`groupid=0` 这种"看起来无害"的参数会直接拒绝——每一步都要拿真实请求验证，不能照抄第三方代码；
3. **浏览器在自动化里应该是"一次性工具"**：只用来完成机器替代不了的人机交互（扫码），登录态落盘后链路应该能脱离浏览器独立运行，这样稳定性才高；
4. **错误码要逐个实验定位**：`-80018` 这种通用错误，固定住其他变量、一次只改一个参数地试，比读文档快得多（这类接口的文档基本不存在）；
5. **内联样式要为深色模式预留**：微信正文用不了 CSS 变量，写死的浅色背景在深色模式下就是白块——装饰性背景一律用半透明色，一套样式两种模式都成立。
