# 📋 背景

## 事件起因

7月22日中午，实验室网络突然不可用。直到22:30才收到通知：有人电脑中木马被基地防火墙拦截，网络从"不限设备数"变成了"认证模式，每账号限制可连接设备数"。

## 核心矛盾

账号设备数受限，但我有TrueNAS物理机上跑着多个虚拟机和服务，都需要联网。

## 解决方案

在TrueNAS上跑OpenWRT虚拟机，将物理网口直通进去，DHCP获取一个IP后通过NAT为多个设备提供网络。

**架构设计：**

```
[Internet]
    |
[基地网络] → 认证模式（1账号=1设备限制）
    |
[TrueNAS 物理机]
    |
    ├── 网口1 → 网桥br0 → OpenWRT WAN
    ├── 网口2 → macvtap → OpenWRT LAN
    └── ...
    |
[OpenWRT 虚拟机]
    |
    ├── DHCP 获取 1 个 IP（WAN口）
    ├── NAT/路由转发
    └── 为多个设备提供网络
```

**核心思路：** 利用OpenWRT的NAT功能，对外只暴露一个DHCP获取的IP，对内通过路由转发为多个设备提供网络。

# 🔧 TrueNAS网桥配置

## 为什么必须组网桥

TrueNAS的虚拟机管理器基于libvirt/QEMU，**不支持直接把物理网口给虚拟机用**。正确做法是在TrueNAS层面把物理网口组成一个Linux Bridge，虚拟机网卡绑定到网桥上。

## 操作步骤

### 1. 查看物理网口

在TrueNAS Web UI中进入 **Network > Interfaces**，查看所有物理网口名称（如`enp7s0`、`enp8s0`、`enp9s0`）。

### 2. 创建网桥

- **Network > Interfaces > Add**
- 类型选择 **Bridge**，名称填`br0`
- 将需要用于OpenWRT WAN的物理网口添加为Member

### 3. 配置网桥网络参数

将原物理网口的网络配置完整迁移到网桥（IP地址、子网掩码、网关、DNS）。

**⚠️ 重要警告：** TrueNAS会弹出以下提示：

> Editing interface will result in default gateway being removed, which may result in TrueNAS being inaccessible.

这个警告的意思是：你正在修改绑定了默认网关的网络接口，系统会清空旧的网关设置，需要在此处重新指定。

**处理方式：**
- 如果IP在同一子网：保持预填的网关值不变，直接保存
- 如果换了子网：必须手动输入新网关
- **操作前**：在另一台电脑打开终端`ping <TrueNAS IP> -t`持续ping，以防失联
- **如果搞砸了**：通过TrueNAS本地控制台（显示器直连）按`Ctrl + Alt + F1`，选择Network Configuration重置恢复

### 4. 测试连接

TrueNAS会提示测试连接，确认更改后生效。

# 📦 OpenWRT虚拟机创建

## 1. 存储准备

在TrueNAS中创建一个ZVOL（约10GB）作为OpenWRT虚拟磁盘。

**关键坑点：** ZVOL大小为10GB，但OpenWRT默认固件只用了约100MB作为根分区，剩余9.9GB未分配。这导致后面的空间不足问题。

## 2. 创建虚拟机

通过TrueNAS Web UI的 **Virtualization** 页面创建虚拟机：
- 名称：`7_openwrt`
- 磁盘：选择上面创建的ZVOL
- CPU：1-2核
- 内存：512MB-1GB
- 引导：上传OpenWRT x86-64镜像（OpenWrt 25.12.5）

## 3. 网络配置

添加两个网卡：
- **网卡1 (WAN)**：绑定到`br0`网桥
- **网卡2 (LAN)**：使用macvtap直通另一个物理网口

macvtap模式让虚拟机网卡直接接入物理网络，性能最好，但会占用物理网口（后面踩了大坑）。

## 问题1：virsh权限错误

### 现象

```
WARNING: Your user does not have sudo privileges so /usr/bin/virsh command will run on your behalf.
error: failed to connect to the hypervisor
error: authentication unavailable: no polkit agent available to authenticate action 'org.libvirt.unix.manage'
```

### 排查过程

**第一步：尝试加入sudo组**

```bash
root@woshicby[~]# usermod -aG sudo woshicby
```

报了一堆SSSD缓存错误：
```
[sss_cache] [confdb_init] (0x0010): Unable to open config database [/var/run/sssd-cache/db/config.ldb]
Could not open available domains
```

这些错误其实是SSSD守护进程没运行导致的噪音，`usermod`本身大概率是成功的。

**第二步：确认组写入成功**

```bash
woshicby% grep ^sudo /etc/group
sudo:x:27:woshicby
```

组文件里确实有`woshicby`，说明写入成功了。

**第三步：测试sudo**

```bash
woshicby% sudo whoami
[sudo] password for woshicby:
woshicby is not in the sudoers file.
This incident has been reported to the administrator.
```

虽然用户在`sudo`组里，但sudoers文件根本不认这个组！

**第四步：检查sudoers**

```bash
root@woshicby[~]# cat /etc/sudoers | grep "%sudo"
root@woshicby[~]#
```

**无输出！** sudoers里根本没有`%sudo`的授权行。

查看完整sudoers内容：
```
root ALL=(ALL:ALL) ALL
truenas_admin ALL=(ALL) ALL
Defaults syslog_goodpri = debug
Defaults secure_path = /sbin:/bin:/usr/sbin:/usr/bin:/usr/local/sbin:/usr/local/bin
Defaults log_subcmds
Defaults log_format=json
```

只有`root`和`truenas_admin`有sudo权限，**没有`%sudo`或`%wheel`组授权**。

### 根本原因

TrueNAS SCALE虽然是Linux（Debian-based），但用户管理沿用FreeBSD传统。sudo授权组是`wheel`，不是`sudo`。`usermod -aG sudo`在标准Linux上管用，在TrueNAS上不管用。

### 解决方案

直接在sudoers里添加用户授权（以root身份执行）：

```bash
visudo
```

在`truenas_admin`那行下面添加：

```
woshicby ALL=(ALL:ALL) ALL
```

保存退出后（nano中按`Ctrl+O`回车保存，`Ctrl+X`退出），**不需要重新登录**，立即生效：

```bash
sudo whoami
# 返回 root 即成功
```

### 教训

TrueNAS/FreeBSD系统的sudo授权组和标准Linux不同。先检查sudoers里实际授权了哪个组，再加组；或者直接在sudoers里加用户行，最快最准。

## 问题2：macvtap设备忙

### 现象

```bash
root@woshicby[~]# virsh start 7_openwrt
error: Failed to start domain '7_openwrt'
error: error creating macvtap interface macvtap3@enp7s0 (00:a0:98:27:5e:41): Device or resource busy
```

### 排查过程

**第一步：检查残留macvtap设备**

```bash
ip link show | grep macvtap
```

无输出，说明没有残留设备。

**第二步：检查物理网卡状态**

发现`enp7s0`已经被网桥`br0`占用了。

### 根本原因

macvtap要求物理网卡**独占**，但`enp7s0`已经作为网桥成员被使用了。一个网卡只能选一种方式：要么给网桥当成员，要么给macvtap独占。

### 解决方案

- macvtap改用另一个没有被占用的物理网口（如`enp8s0`）
- 如果有残留的macvtap设备：`ip link delete macvtap3`
- 重启libvirtd：`systemctl restart libvirtd`

### 教训

macvtap和网桥不能共用同一个物理网口。规划网口分配时，每个口只能选一种用途。

## 问题3：virsh控制台会话冲突

### 现象

```bash
root@woshicby[~]# virsh console 7_openwrt
error: operation failed: Active console session exists for this domain
```

### 原因

之前打开的virsh console没有正常退出——直接关了终端，没有按`Ctrl + ]`退出，导致会话一直挂在后台。

### 解决方案

```bash
# 方法一：强制接管（最快）
virsh console 7_openwrt --force

# 方法二：杀掉旧会话
ps aux | grep "virsh console" | grep -v grep
kill <PID>

# 方法三：重启libvirtd（慎用，影响所有虚拟机）
systemctl restart libvirtd
```

### 预防

退出virsh console时按`Ctrl + ]`，不要直接关终端。

## 问题4：主机名冲突（mDNS抢注）

### 现象

`ping woshicby.local`解析到的IP是飞牛OS设备，而不是TrueNAS。

### 排查过程

1. `ping -4 woshicby.local` → 得到飞牛OS的IP
2. 确认`.local`是mDNS域名，谁先响应谁就赢
3. 局域网内两台设备（TrueNAS和飞牛OS）主机名都叫`woshicby`，mDNS广播竞争中飞牛OS抢到了应答权

### 解决方案

1. 登录飞牛OS后台，把主机名改为`feiniu-cby`
2. 重启飞牛OS的avahi/mDNS服务（或直接重启系统）
3. TrueNAS直接使用IP访问，在路由器做IP/MAC绑定

### 教训

局域网内不要有两台设备用同一个主机名。mDNS没有冲突解决机制，谁快谁赢。

## 问题5：TrueNAS更新后OpenWRT异常

### 背景

TrueNAS升级到25.10.5，更新内容包括：
- Linux内核升级到v6.12.95（修复CVE-2026-43503和CVE-2026-46331等本地权限提升漏洞）
- 修复控制台内存泄漏（getty@tty1）
- 修复smartctl输出解析、TrueCloud Backup卡死等问题

### 现象

更新后OpenWRT虚拟机：
- 能ping通LAN IP
- 管理网页只显示"LuCI - Lua Configuration Interface"标题，内容空白
- 无法访问外网

### 调试步骤

**第一步：确认ping范围**

```
LAN IP → 通
8.8.8.8 → 不通
baidu.com → 不通
```

**第二步：检查Web服务**

```bash
ps | grep uhttpd  # 有运行
```

**第三步：检查防火墙**

```bash
/etc/init.d/firewall stop  # 网页仍空白
```

**第四步：检查WAN口**

```bash
ifconfig eth1  # WAN口无IP
```

**第五步：检查路由**

```bash
route -n | grep UG  # 无默认网关
```

### 解决方案

**LuCI空白页：**

```bash
# 清除Lua缓存（90%的空白页是它造成的）
rm -rf /tmp/luci-*
/etc/init.d/uhttpd restart
```

**无法上网：**

```bash
# 重启WAN接口
ifdown wan
ifup wan

# 修复DNS
echo "nameserver 114.114.114.114" > /tmp/resolv.conf
cp /tmp/resolv.conf /etc/resolv.conf
```

### 根本原因

内核更新后虚拟网卡驱动变化，导致WAN口DHCP续租失败 + Lua JIT编译异常（LuCI缓存不兼容）。

### 教训

TrueNAS内核更新可能影响虚拟化驱动和虚拟机内的网络行为，更新前先备份虚拟机配置。

## 问题6：AdBlock-Fast启动失败（缺依赖 + 空间不足）

### 现象

```
AdBlock-Fast - 状态
服务状态
版本 1.2.4-r4 - 启动失败.
服务警告
缺少推荐的软件包：'grep, sed'
```

### 第一步：尝试安装依赖

OpenWRT 25.12版本使用`apk`而非`opkg`：

```bash
apk add grep sed gawk coreutils-sort
```

结果全部失败：`ERROR: No space left on device`

### 第二步：诊断空间

```bash
root@OpenWrt:~# df -h
Filesystem                Size      Used Available Use% Mounted on
/dev/root                98.3M     96.2M      8.0K 100% /
tmpfs                   238.2M     11.2M    227.0M   5% /tmp
/dev/vda1                16.0M      6.2M      9.8M  39% /boot
```

根分区只有98.3MB，已100%占用。

### 第三步：查看分区表

```bash
root@OpenWrt:~# cat /proc/partitions
major minor  #blocks  name
 254        0   10485776 vda
 254        1      16384 vda1
 254        2     106496 vda2
 259        0        239 vda128
```

`vda`总容量10GB，`vda1` 16MB（boot），`vda2` 104MB（root），剩余9.9GB未分配。

### 第四步：定位空间杀手

```bash
root@OpenWrt:~# du -sh /usr/bin/* | sort -hr
25.7M   /usr/bin/cloudflared
15.0M   /usr/bin/cs-firewall-bouncer
1.3M    /usr/bin/aria2c
928.0K  /usr/bin/openssl
468.0K  /usr/bin/gawk
```

`cloudflared`（Cloudflare Tunnel客户端，25.7MB）和`cs-firewall-bouncer`（CrowdSec防火墙联动，15MB）占了40MB。

### 第五步：释放空间

```bash
# 确认未运行
ps | grep cloudflared
ps | grep cs-firewall-bouncer

# 删除
rm -f /usr/bin/cloudflared
rm -f /usr/bin/cs-firewall-bouncer

# 确认
df -h /
# /dev/root  98.3M  55.5M  40.7M  58% /
```

释放了40MB。

### 第六步：安装分区工具

```bash
apk update
apk add fdisk e2fsprogs gdisk
```

### 第七步：查看分区表

```bash
root@OpenWrt:~# fdisk -l /dev/vda
GPT PMBR size mismatch (246304 != 20971551) will be corrected by write.
The backup GPT table is not on the end of the device.
Disk /dev/vda: 10 GiB, 10737434624 bytes, 20971552 sectors
Disklabel type: gpt

Device      Start    End Sectors  Size Type
/dev/vda1     512  33279   32768   16M Linux filesystem
/dev/vda2   33280 246271  212992  104M Linux filesystem
/dev/vda128    34    511     478  239K BIOS boot
```

**关键：** `vda2`的起始扇区是**33280**，这个数绝对不能变。分区表是GPT格式，有备份表位置不匹配的警告。

### 第八步：使用gdisk扩展分区

```bash
gdisk /dev/vda
```

交互操作：
1. `p` → 确认`vda2`起始扇区为33280
2. `d` → `2` → 删除分区2
3. `n` → `2` → 新建分区2
   - First sector: **33280**（必须手动输入，不能用默认值！）
   - Last sector: 直接回车（用最大空间）
   - Hex code: 直接回车（默认8300）
4. `p` → 再次确认起始扇区为33280，结束扇区接近20971518
5. `w` → `Y` → 写入并退出（gdisk会自动修复备份GPT表）

### 第九步：重启

```bash
reboot
```

### 第十步：扩展文件系统

```bash
resize2fs /dev/vda2
df -h /
# /dev/root  9.8G ... 可用空间超过 9GB
```

### 第十一步：安装依赖并启动服务

```bash
apk update
apk add grep sed gawk coreutils-sort
/etc/init.d/adblock-fast restart
/etc/init.d/adblock-fast status
```

### 教训

- OpenWRT在虚拟机中运行时，默认固件的根分区只有约100MB，装不了几个包就满了
- 一定要在创建虚拟机后第一时间扩容分区
- 扩容的关键：起始扇区不能变，GPT分区表用gdisk（fdisk对GPT支持有限）
- 如果空间不足导致无法安装分区工具，先删除不必要的程序腾出几MB

## 问题7：OpenWRT使用apk而非opkg

### 发现

OpenWRT 25.12版本开始使用`apk`（Alpine Linux包管理器）替代传统的`opkg`。

| opkg (旧版) | apk (25.12+) |
|---|---|
| `opkg update` | `apk update` |
| `opkg install <包名>` | `apk add <包名>` |
| `opkg remove <包名>` | `apk del <包名>` |
| `opkg list-installed` | `apk list -I` |

### 教训

网上很多OpenWRT教程还在用opkg，25.12以后的版本已经换成了apk，命令不同。查教程时注意版本。

# 📝 经验总结

## 1. 提前准备的重要性

如果之前就有OpenWRT方案，网络模式变更时不会这么被动。花了约32小时（实际集中工作时间约1天），网络中断的焦虑和碎片化排查拉长了总时长。

## 2. 网桥是虚拟机网络的核心

TrueNAS等NAS系统跑虚拟机，必须先组网桥再给虚拟机用。macvtap需要独占物理网卡，和网桥不能共用同一个口。

## 3. OpenWRT存储空间陷阱

虚拟机部署OpenWRT时，默认固件根分区只有约100MB。一定要在创建后第一时间扩容分区（用gdisk处理GPT分区表 + resize2fs扩展文件系统）。扩容的关键是起始扇区不能变。

## 4. TrueNAS更新风险

内核更新可能影响虚拟化驱动，导致虚拟机网络异常。更新前先备份虚拟机配置。

## 5. FreeBSD vs Linux权限模型

TrueNAS SCALE虽然是Linux，但用户管理沿用FreeBSD传统。sudo授权组是`wheel`，不是`sudo`。`usermod -aG sudo`在Linux上管用，在TrueNAS上不管用。

## 6. mDNS没有冲突解决机制

局域网内不要有两台设备用同一个主机名，mDNS谁快谁赢。

## 7. OpenWRT 25.12换包管理器了

从opkg换成了apk，网上教程大部分还在用opkg，注意区分。
