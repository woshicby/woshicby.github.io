# 用 ADB 给安卓手机做故障取证：一次"盲操作 GUI"的完整记录与能力边界

> 一条微信里模糊到没有信息量的报错——「网络异常，稍后重新进入」——最后变成了一份带字节级证据的工单。
> 这篇文章记录过程，也如实交代：**让 AI 去操作图形界面，到底有多费劲，边界在哪。**

---

## 0. 场景

手机上的微信「贴图号」出了个毛病：

```
我 → 作品 → 右上角铃铛 → 「赞」标签
→ 一直显示"网络异常，稍后重新进入"，看不到点赞列表
→ 铃铛上的 +10 未读角标一直不消
```

报错长这样：

*▲ 图 1：四个标签是 留言 / **赞 +10** / 关注 / 私信，当前停在「赞」上，正文只有一句"网络异常，稍后重新进入"。*

入口是「我 → 作品」，铃铛上的红色角标就是那个消不掉的 +10：

![作品页铃铛 +10 角标](./images/post.36.20261008/02-作品页铃铛加10角标.png)

*▲ 图 2：「作品」页右上角，铃铛上挂着 +10 的未读角标。*

最奇怪的地方在于：**同一个页面的另外三个标签——留言、关注、私信——全部正常。**

![同页私信标签正常](./images/post.36.20261008/03-同页私信标签正常.png)

*▲ 图 3：同一页面的「私信」标签——正常加载出两条通知。*

![同页关注标签正常](./images/post.36.20261008/04-同页关注标签正常.png)

*▲ 图 4：同一页面的「关注」标签——正常渲染出"暂无关注"的空状态。*

（「留言」标签也正常加载出了一整个评论列表。因为内容含其他用户的昵称和评论，这里不放图。）

同一个页面、同一次会话、同一张网络，**三个正常、一个报错**——这就是整件事的起点。

手机连着电脑、开发者模式开着。于是决定不走"你说我猜"，而是用 ADB 把这件事查穿。

环境：

| 项 | 值 |
|---|---|
| 设备 | 红魔 NX809J（1216×2688，density 520） |
| 系统 | Android 16（SDK 36） |
| 微信 | 8.0.78（当前最新正式版） |
| root | **无**（`su` 不存在） |
| `adb shell` 能力 | `CapEff=0`，组里没有 `net_raw` |
| adb | platform-tools 37.0.1（现装的，没现成环境） |

还有一个容易忽略的前置细节：这台手机开了**应用分身**（中兴/红魔 ROM 的 double layer），微信在主账号和分身里各装了一份（uid 分别是 10525 / 99910525）。查任何系统级状态（崩溃、流量、连接）之前，得先确认报错页面属于哪个实例——最后的流量实测都锚定在主账号实例（uid 10525）上，系统 dropbox 里唯一一条微信相关的 ANR 属于分身实例（uid 99910525），且是 2026-10-05 的旧记录，与本案无关。**先分清实例，再谈证据**，否则很容易拿错对象的数据去下结论。

## 1. 怎么把"网络异常"变成可交付的证据

### 1.1 第一堵墙：日志根本不存在

第一反应当然是抓日志。结果：

```bash
$ adb shell logcat -d | wc -l
0
$ adb shell "getprop | grep -i logd"
[init.svc.logd]: [running]        # logd 进程在跑，但……
[log.tag]: [S]                    # ← 全 tag 静默
$ adb shell "logcat -g -b main"
main: ring buffer is 4 MiB (2 MiB consumed, 0 B readable)
```

`log.tag = S`（Silent）意味着**日志从源头就没写**——进程还在、缓冲区还在，但读出来永远是 0 行，`log -t TAG msg` 也不回显。国产 ROM 把日志整体静音了，这条路直接判死，别在上面耗时间。

日志这条路判死后，顺手把微信自己的日志也翻了个底朝天：

```bash
adb shell "ls -la /sdcard/Android/data/com.tencent.mm/MicroMsg/xlog/"
# APPBRAND0_20261006.xlog   34 MB   ← brandservice（视频号/贴图号）进程
# PUSH_20261007.xlog        41 MB
# TP_20261007.xlog          335 KB
```

mars xlog 是**压缩 + 加密**的（块头 `0c` = async zstd），可读的只有每块首尾几十字节。试过 zlib 逐偏移爆破、也装 zstandard 解过——都解不出来，密钥在 App 私有目录里，无 root 拿不到。**这条路也别指望。** 另一个旁证位置是 `cache/<32位hash>/bizcache/` 里的 `profile_resp_*` 响应缓存：故障时刻该目录**没有新文件写入**，佐证"这次请求没成功落盘"。

### 1.2 于是换打法：行为对照实验

日志拿不到，就拿行为。把每个可疑假设都设计成一个可执行的实验：

| 假设 | 实验 | 结论 |
|---|---|---|
| 网络问题 | 关 WiFi 走 5G 流量，同一路径复测 | ❌ 同样报错 |
| 网络问题 | ping `dns.weixin.qq.com` / `short.weixin.qq.com` | 全通，25~38ms |
| 代理/Private DNS | `settings get global http_proxy` / `private_dns_mode` | 都是 null |
| 页面级问题 | 同页面另外三个标签 | ✅ 全部正常 |
| 客户端崩溃 | `dumpsys dropbox --print` | 无相关记录 |
| 本地状态问题 | `am force-stop` 后重启微信 | ❌ 照旧 |
| 版本问题 | 查最新版本号 | 已是最新 |
| 缓存问题 | 清缓存（见 1.5） | ❌ 照旧 |

到这一步，"网络问题"基本被证伪了。但还不能说清楚**到底卡在哪一环**——是请求没发出去，还是发出去没回包，还是回包了处理失败？这需要一个"无 root 的抓包"。

**版本核对也值得单独记一笔**：应用商店里写的"最新版本 8.3.50"是个坑——那是**微信的旧编号体系**，当前版本实际显示 8.0.78。差点拿一个不存在的版本号去下旧包，**核对版本要以 App 内实际显示为准，别信商店页面**。

### 1.3 无 root 的"等效抓包"：按 UID 计字节

没法 tcpdump（没有 `CAP_NET_RAW`、设备里也没有 tcpdump），但 Android 有个被低估的东西：

**netstats 的 eBPF map，能拿到按 UID 的实时字节计数。**

```bash
adb shell "dumpsys netstats detail" \
  | sed -n '/mAppUidStatsMap/,/mStatsMapA/p' \
  | awk '$1==10525 {print $2,$3,$4,$5}'
# 输出：rxBytes rxPkts txBytes txPkts（累计值，一次读取约 0.3 秒）
```

读到的是累计值，做差值就是窗口流量。于是设计了一个 12 秒窗口的对照实验——空闲做噪声基线，失败的「赞」和同页正常的标签交替触发：

| 窗口 | 收到 RX | 发出 TX |
|---|---|---|
| ① 空闲（噪声基线） | +88 B | +4256 B |
| ② 点「留言」（**正常**） | +11171 B | +1052 B |
| ③ **点「赞」（报错）** | **+12745 B** | **+492 B** |
| ④ 再点「赞」 | +12797 B | +544 B |
| ⑤ 点「关注」（正常） | +1858 B | +2352 B |
| ⑥ **第三次点「赞」** | **+12745 B** | **+492 B** |
| ⑦ 点「私信」（正常） | +436 B | +80 B |

这张表直接回答了三个问题：

1. **请求确实发出去了**——TX 有 ~492 字节，客户端没在本地就把路堵死。
2. **服务端确实回包了**，而且回的量（12.7KB）和正常能加载的「留言」（11.2KB）**同一量级**。所以不是超时、不是空响应。
3. **③ 与 ⑥ 逐字节相同**——确定性响应，基本排除偶发与网络抖动。

结论从"网络异常"升级为：

> 请求已正常发出，服务端已正常回包，**客户端拿到响应后处理失败**，才兜底显示了"网络异常"。

连接级再补一刀：前后各快照一次 `/proc/net/tcp6`，比对出「点赞」瞬间新增的两条连接，端点 `116.130.175.129` / `116.130.175.71`，反查归属是**中国联通天津 AS4837——微信接入层**。

这个方法的局限也要如实说：微信走 mmtls 加密 + 证书固定，字节计数只能证明"发了多少、回了多少"，**拿不到 payload**。想知道回包里到底写了什么，只有服务端日志能回答——这正是工单最后那句话的由来。

### 1.4 误差出现的时机：1 秒内

还有一个便宜的旁证：点击后按 1s / 3s / 8s 截图，比对 PNG 文件尺寸——错误页是大面积纯色，压出来只有 **61~62 KB**；正常内容页约 **600~610 KB**。结果：**1 秒内就已经是错误页**。秒失败是业务错误/数据异常的形态，超时（网络/域名不通）一般要 5~10 秒才出兜底文案。两条证据指向同一处。

### 1.5 清缓存：全程唯一先停下来问用户的操作

排除缓存之前先查了微信「存储空间」页的自述：已用 39.7 GB，其中**缓存 10.5 GB，里面含聊天记录中的 3.2 GB 原图/原视频**。清掉它，聊天里的老图老视频就会变成"已过期或被清理"——这是**有用户可见代价**的动作，所以先停下来问，用户确认后才动手。

```bash
adb shell pm                          # 先确认 usage 里有 --cache-only！
adb shell pm clear --cache-only com.tencent.mm
```

这条命令本身也踩了坑：在本 ROM 上 **300 秒都没返回**（只能 `ls`/`du` 确认数据目录还在、App 没被卸载，然后等它自己走）——**任何 ROM 上跑 `pm clear` 类危险开关前，先无参 `adb shell pm` 确认支持哪些 flag**，`--cache-only` 不是默认就有的。稍后微信自己的清理流程被触发（「已清理 5.0 GB / 预估 7.3 GB」），最终：

| 位置 | 清理前 | 清理后 |
|---|---|---|
| 外部 `cache/` | 591 MB | 70 KB |
| 外部 `MicroMsg/` | 1.1 GB | 6.1 MB |

清完之后，故障**完全不变**。缓存因素正式出局。

### 1.6 这条证据链的价值

原来能说的是：

> "我点不了赞，显示网络异常。"

后来能说的是：

```
请求已发出（TX≈492B）、服务端已回包（RX≈12745B，两次一致），
同页其他三个标签正常，双网络/重启/清缓存/版本全部排除，
判断为服务端返回数据或客户端解析失败，请查服务端日志。
```

后者才是能推动问题解决的东西。提交工单时用的就是这张图：

## 2. 真正费劲的部分：我怎么在 GUI 里"动手"

诊断靠读，动手靠点。而**点，是这件事里最不体面的部分。**

### 2.1 视觉模型给的坐标不能用

第一反应是截图丢给视觉模型问"这个按钮在哪"。实测：**偏差能到 200px**。

最惨的一次：问"留言/赞/关注/私信 四个标签的坐标"，得到的答案信心十足，然后点下去——点开了**朋友圈相册**。

教训：**视觉模型适合"读文字"，不适合"报坐标"。** 坐标要靠像素自己算：

```python
from PIL import Image
import numpy as np

a = np.array(Image.open('screen.png').convert('L')).astype(int)
sub = a[:, 100:520]                  # 只看左对齐文字列
rs = (sub > 110).sum(axis=1)          # 阈值后按行聚类 → 每行文字带的 y 中心
```

- 行带间距 ~145-150px 是正常菜单行距；
- 把"行带序号"和视觉模型读出的"标签顺序"对齐，就能得出**第 N 行是哪个菜单项**；
- 红色未读角标用 RGB 阈值定位最准：`R>150 & G<90 & B<90`——图 1、图 2 里的那个红角标就是这么找到的，往左下偏一点就是铃铛图标中心。

### 2.2 每一步都必须回读状态

点击之后的验证靠系统状态，不靠"看起来对了"：

```bash
adb shell "dumpsys activity activities | grep topResumedActivity"
```

进错页面就 `input keyevent 4` 逐级退回。这里有个坑：

> `am start -n pkg/.ui.LauncherUI` 在 App 已有任务栈时**不会回到首页**，只会把该任务恢复到栈顶页面。要回首页必须连续按返回键，每步校验。

### 2.3 输入中文：这一关最难受

事实清单：

- `adb shell input text "中文"` → `NullPointerException: Attempt to get length of null array`，**CJK 直接不支持**；
- 就算发 ASCII，`input text` 因为发送太快会被输入法丢字母（"tietuhao" 变成 "ie'tu'h'tao"）；
- 想走剪贴板？Android 10+ 剪贴板受前台应用限制，`service call clipboard` 抛 `Not a data message`，也没有 `cmd clipboard`。

唯一可行的路：**走输入法的拼音候选流程。**

```bash
# 字母键码 a-z = 29-54，空格 = 62，退格 = 67
adb shell 'send() { for k in "$@"; do input keyevent $k; sleep 0.2; done; }
           send 48 37 33 48 49 36 29 43; send 62'   # → 上屏「贴图号」
```

- 每个字母间隔 ≥0.15s，写在**设备端 shell 循环**里（避免每个字母一次 adb 往返）；
- 空格键把候选第 1 位提交进输入框，一个词一次空格，如此逐词拼句子；
- **候选第一位不保证正确**：`zan` → 咱（不是赞）、`qing` → 请（不是清）。用词不用字（`dianzan`→点赞、`qingli`→清理）能大幅提高命中率；
- 速度：**一条 60 词的中文 ≈ 380 次按键 ≈ 100~130 秒。**

### 2.4 两个让人崩溃的隐性坑

**坑一：输入法会进入"只保留最后一个字母"的坏状态。**

多字母拼音不进缓冲、候选只剩单字，看起来像"打字没反应"。排查很久才发现，是之前误触键盘把输入法模式切乱的后果。

```bash
adb shell am force-stop com.tencent.qqpinyin   # 重置输入法进程
```

**这一下就好了。** 事后看，这是整个过程中性价比最高的一条命令。

**坑二：键盘开合会挪动输入框的位置。**

| 状态 | 输入框位置 |
|---|---|
| 键盘收起 | 屏幕底部，y ≈ 0.95H |
| 键盘展开 | 上移到 y ≈ 0.80H |

而我一直按"底部"去点——**点到的全是键盘按键**，于是又切模式、又打乱输入法……形成恶性循环。

正确顺序：**先关键盘 → 点底部输入框 → 之后不要再点任何地方，直接打字。**

### 2.5 校验：别去读小字

输入框和候选栏里的字号太小，视觉模型反复误读（同一张图能读出三种不同结果）。

可靠的校验信号反而是这些"结构性"的：

- **「发送」按钮是否出现**——绿块颜色阈值检测，能判断输入框是否非空；
- **两张截图的像素差**——能精确定位"输入法真的响应在哪一行"；
- **已发送的消息气泡**——字大，是最终校验里唯一靠谱的读数方式。

### 2.6 选图：绝不能赌

提交工单要传截图。相册里混着用户自己的照片，**点错就是把私人照片传到外部系统**。

做法是让正确性变得"机器可验证"：

1. 给要上传的图加一圈**品红 28px 边框**；
2. `adb shell touch <file>` 把时间改成最新 + 触发媒体库重扫 → 自己的图排在相册最前（`adb push` 会保留源文件 mtime，不 touch 就排不最前）；
3. 在相册网格里按品红像素精确定位（实测拿到 4 条竖边的 x 坐标，正好对应 3 张图的边界）；
4. 回表单后，用「边框像素 + 平均亮度/亮像素占比」复核缩略图确实是自己的图（白底文档 ~59% 亮像素 vs 深色截图 ~1%，一目了然）。

用户中途手工补了两张图，我用同样的方法复核确认无误，才点的提交。

### 2.7 两条走不通的岔路

顺手记两条死路，免得后来人再撞：

- **PCAPdroid（免 root 抓包）装不上**：`adb install` 报 `SecurityException: Caller has no access to session -1`（`--no-streaming`、push + `pm install` 都一样），手机还弹出 `UsbAccountCheckPswdActivity`——中兴/红魔 ROM 要求**用户本人验证账号密码**后才允许 USB 安装。这类验证框绝不能代劳，只能把 APK 推到 `/sdcard/Download/` 让用户自己装、自己过验证。何况装上了也只能多拿到域名/IP（mmtls 内容照样加密），不如字节计数省。
- **写系统剪贴板**：`service call clipboard 2 ...` 返回 `Not a data message`，`cmd clipboard` 提示没有 shell 实现——Android 10+ 这条路彻底不通，中文输入只能走 2.3 的拼音流程。

## 3. 能力边界：让 AI 操作 GUI，能做什么、做不了什么

这一节是这篇文章真正想留下的东西。

### ✅ 可靠能做的

- **像素级读屏**：颜色、亮度、文字行位置、图标簇、角标——自己算，比问模型准；
- **读系统状态**：`dumpsys` / `am` / `pm` / `getprop` / `/proc/*` / netstats；
- **发输入事件**：`input tap` / `swipe`（带 duration 可模拟长按）/ `keyevent`；
- **文件推送拉取**、媒体库注入；
- **长流程编排 + 每步闭环校验**：这是最大的优势——不会烦、不会漏、每一步都留证据。

### ❌ 做不好 / 做不了的

| 边界 | 具体表现 |
|---|---|
| **看小字** | UI 里的小号文字（输入框、候选栏、状态行）视觉模型反复误读，只能靠结构性信号替代 |
| **"哪里能点"是盲的** | 没有任何语义化的可点控件信息，只能从像素特征反推；**坐标错一次就可能删错数据、发错消息** |
| **输入非 ASCII 文本** | 没有可用的剪贴板写入；只能逐字母拼音 + 候选上屏，慢且候选首位不保证 |
| **手势** | 长按、拖拽、双指缩放、带惯性的滑动，都只能近似 |
| **读 App 私有数据** | 无 root 时 `/data/data/*` 不可见；ROM 静音的日志、加密的 xlog 都读不出来 |
| **抓原始网络包** | 无 root + shell 无 `CAP_NET_RAW` → 只能退到"按 UID 字节计数 + TCP 连接表" |
| **安装应用** | 国产 ROM 可能直接拦掉 `adb install`（`SecurityException: Caller has no access to session -1`），还要用户本人过账号密码验证 |
| **界面的"活的"** | 页面会自己重绘、列表会滚动、键盘会挪位置——刚测的坐标下一秒可能失效 |
| **密码与验证码** | 绝不代输、绝不代收；必须由用户本人完成 |

### 效率的真实量级

| 动作 | 代价 |
|---|---|
| "看清一屏" | 1 次截图 + 1 次像素分析 |
| 一次点击 | 1 次 adb 调用（含等待 0.3~5s） |
| 一条 60 词中文 | ≈380 次按键 ≈ 100~130 秒 |
| 整件事 | 23:07 → 00:28 共 **81 分钟**，350+ 次工具调用 |

**GUI 是为人眼和手指设计的。** Agent 操作它的本质是：**高延迟的 I/O，加上没有触觉的盲操作。** 所以真正决定成败的不是"能不能点"，而是**每一步之后能不能读回状态确认**。

## 4. 方法论：把 GUI 自动化当成分布式系统来做

这次沉淀下来四条：

1. **闭环**：观测（截图）→ 建模（像素分析）→ 动作（输入事件）→ **校验（状态回读）**。
   「工具返回成功」≠「事情成了」——`input tap` 永远返回成功，包括点在键盘上的时候。
2. **对照实验 > 看日志**：当日志不可得（ROM 静音、无 root），就用受控对照把假设一个个证伪，而不是等一条日志自己出现。
3. **把"选对"变成可验证的**：涉及误操作代价高的动作（选图、删数据），先给目标加"机器可检的标记"，再动手。
4. **不确定就停下问人**：清 10.5GB 缓存（会清掉聊天里的原图原视频）、往腾讯提交工单——这类**有用户可见代价**的动作，宁可停下来等确认。

## 5. 复现命令清单

```bash
# —— 环境与状态 ——
adb devices -l
adb shell "getprop ro.product.model; getprop ro.build.version.release"
adb shell "dumpsys package com.tencent.mm | grep versionName"
adb shell "dumpsys activity activities | grep topResumedActivity"
adb shell "cat /proc/self/status | grep CapEff"     # 0 = 无原始套接字能力
adb shell pm list users                             # 应用分身：分清 u0 / u999 实例

# —— 日志（多半不可得，但先探边界）——
adb shell "logcat -d | wc -l"                       # 恒为 0 行 = ROM 静音
adb shell "dumpsys dropbox --print"                 # 崩溃/ANR 替代取证
ls /sdcard/Android/data/com.tencent.mm/MicroMsg/xlog/   # 微信 xlog（压缩/加密，仅首尾明文）

# —— 无 root 的"等效抓包" ——
adb shell "dumpsys netstats detail" \
  | sed -n '/mAppUidStatsMap/,/mStatsMapA/p' | awk '$1==<uid> {print $2,$3,$4,$5}'
adb shell "cat /proc/net/tcp6 > /sdcard/sk.txt"     # 重定向必须在设备端执行

# —— UI 操作 ——
adb shell input tap X Y
adb shell input keyevent 4                          # 返回；67 退格；62 空格
adb shell 'for k in 47 36 49 43 32 33; do input keyevent $k; sleep 0.2; done'  # 慢速拼音

# —— 输入法坏状态急救 ——
adb shell am force-stop com.tencent.qqpinyin

# —— 让图排在相册最前 ——
adb shell touch /sdcard/Pictures/<dir>/<file>.png
adb shell am broadcast -a android.intent.action.MEDIA_SCANNER_SCAN_FILE \
  -d file:///sdcard/Pictures/<dir>/<file>.png

# —— 危险开关：确认支持 --cache-only 之前，绝不能跑 pm clear ——
adb shell pm                                          # 看 usage 里有没有 --cache-only
adb shell pm clear --cache-only <pkg>
```

## 7. 结语

整个过程最反直觉的一点是：

**难的不是"做诊断"，而是"动手"。**

诊断部分——对照实验、字节计数、连接表反查——是干净、优雅、可复现的。
动手部分——找坐标、点按钮、打中文、别选错图——是粗糙、易碎、充满意外的。

如果要从这次经历里抽出一条最通用的经验，我会选这条：

> **在 GUI 里，永远不要相信"应该点对了"。**
> 让每一个动作后面都跟一次状态回读，让每一个有代价的选择都变得可机器校验。

—— 记于一次凌晨两点的手机取证之后。
