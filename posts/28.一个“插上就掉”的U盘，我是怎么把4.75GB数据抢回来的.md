一次关于虚焊、Phison 主控冷热配置差异、以及“窗口期抢数据”的完整实战记录。

## 背景

手头有一个 MSI 主板附带的 U 盘，量产形态很特殊：**同一个 USB 设备枚举出两个盘** —— 一个是虚拟光驱（`E:`，里面是 MSI 主板驱动光盘，4.76GB CDFS），一个是实际存储盘（`H:`，24.5GB FAT32）。主控是 Phison PS3281B（USB 层显示 `VID_346D&PID_5678`）。

某天在 Mac 上用过之后，拿回 Windows 插上，问题出现了：

> **一插上就掉。** 设备枚举出来 → 几秒后消失 → 重新枚举 → 又掉，循环往复。同时系统日志里 `cdrom` 事件疯狂刷屏（2 小时 279 条 `Event 51`，报错内容是 `An error was detected on device \Device\CdRom1 during a paging operation`）。

最初以为又是 Mac 格式化导致的分区表问题（APFS/HFS+ 在 Windows 上不认是很常见的事），但检查下来发现事情没那么简单。

## 诊断过程

### 第一步：确认盘的状态

```powershell
# 磁盘层面
Get-Disk -Number 3
# PartitionStyle : RAW
# OperationalStatus : No Media   ← 关键：无介质
# Size : 0

# 分区层面：一个分区都没有
Get-Partition -DiskNumber 3
```

`No Media` 是设备在 SCSI 协议层报告的状态 —— **主控认为自己没有介质**。这不是分区表读不出来，而是存储层就不存在。排除 APFS/HFS+ 的可能。

### 第二步：绕开 Windows 存储栈，直接问主控

Windows 的存储驱动在 `No Media` 状态下会挡住一切访问（`ERROR_NOT_READY`）。我用 `DeviceIoControl(IOCTL_SCSI_PASS_THROUGH_DIRECT)` 直接向物理盘发 SCSI 命令，绕过了存储栈：

```
INQUIRY:          status=0 (主控活着, 识别为 FC 3281B)
TEST_UNIT_READY:  status=2 → Sense: NOT READY / ASC=0x3A = MEDIUM NOT PRESENT
READ_CAPACITY_10: status=2 → 同样 MEDIUM NOT PRESENT
START_STOP_UNIT:  status=0 (命令被接受, 但介质仍未就绪)
```

结论：**主控固件正常（能应答、能收命令），但它明确报告"介质不存在"** —— 主控和 NAND 闪存芯片之间的通信断了。数据在 NAND 里，但主控"看不见"它。

### 第三步：交叉验证

在 Mac 上试：同样"刚插入正常，然后掉盘"。两个系统表现一致 → 彻底排除操作系统/驱动因素，实锤**硬件层问题**。

### 最终诊断：Phison 主控的"冷热配置"差异 + NAND 虚焊

诊断过程中发现了一个关键现象，**软件热重启和物理断电重启，主控加载的配置完全不同**：

| 触发方式 | 主控行为 | 设备身份 |
|---|---|---|
| **冷启动**（物理断电/拔插） | 加载**量产配置**（含虚拟光驱 CD-ROM LUN） | `VendorC ProductCode` / `VID_346D&PID_5678` |
| **热重启**（`pnputil /restart-device` 等） | 加载**出厂默认配置**（无 CD-ROM，双 Disk LUN） | `FC 3281B` / `VID_346D&PID_3281` |

而"插上正常几秒 → 发热 → 掉盘"的模式，正是 **NAND 虚焊（冷焊点）的热敏性特征**：冷态金属收缩，引脚与焊盘刚好压紧能通；运行发热后 PCB 与引脚热膨胀系数不同，虚焊点被撑开，接触断裂。这解释了为什么 Mac/Windows 表现完全一致，也解释了为什么每次插入都有一段"正常窗口期"。

## 抢救思路：利用"窗口期"

关键洞察有两个：

1. **虚拟光驱的内容不依赖 NAND 芯片** —— 它是主控量产时烧录的镜像，存在 NAND 的隐藏保留区。也就是说，只要主控加载了量产配置，`E:` 的光盘内容就能读出来，**跟存储盘 No Media 无关**。
2. **每次插入都有几秒到几十秒的正常窗口** —— 冷态焊点接触良好，此时可以读取。

于是策略变成：**窗口期抢数据** —— 插上瞬间开始读取，掉盘就等重枚举，循环直到全部拷完。

## 抢救脚本的演进（踩坑记录）

### v1：朴素的全量拷贝（失败）

直接从 `E:\` 拷贝到桌面目录，遇到掉盘就卡死。`Permission denied` 刷屏 —— 后来才知道，**掉盘时 CDFS 驱动报的是 `Errno 13 (Permission denied)` 而不是 I/O error**，这个坑后面反复踩。

### v2：循环重试（仍失败）

加了"掉盘 → 等待重枚举 → 继续"的逻辑，但把 `Permission denied` 当成永久错误无限重试，卡在同一批文件上打转。而且每次窗口都从第一个文件开始重新跳过已拷文件，窗口利用率极低。

### v3/v4：清单缓存（有进展但低效）

把光盘文件清单缓存到本地（光盘内容固定不变），窗口内不再重新扫描。但发现一个致命问题：**每次窗口都重新核对 5000+ 个已有文件，还没轮到缺失文件就掉盘了** —— 36 秒窗口全部浪费在跳过已有文件上。

### v5：小文件优先（有 bug）

按文件大小升序排列，先啃小的积累成果。但引入了**假完成 bug**：掉盘时 `PermissionError` 被误判为"永久读不了"（`'dead'`），74 个文件在同一秒被全部放弃，然后 pending 清空 → 假完成。这是整个抢救中最危险的时刻，差点让数据救不回来。

### v6：最终版（成功）

```python
# 核心逻辑：失败时先查盘，盘在才算永久失败
r = copy_one(src_f, dst_f)
if r is True:
    # 成功，移出清单
elif not drive_ready():
    # 盘掉了 → 保留清单，等下一窗口
    break
else:
    # 盘在但失败 → 累计失败次数，>=5 次才确认读不了
    stats['fail_count'][src_f] += 1
```

要点：
- **掉盘感知**：任何失败先检查 `E:` 是否还可达 —— 不可达就是掉盘（保留清单），可达且同一文件连续失败 5 次才标记"确认读不了"
- **断点续传**：目标文件已存在部分大小，就 `seek` 到源文件的对应偏移继续 append —— 每次窗口拷贝的进度不丢
- **小文件优先**：窗口内按源文件大小升序，先完成小文件积累成果，大文件（`MSI Center_2.0.24.0.exe` 550MB）靠断点续传分多个窗口慢慢啃
- **状态持久化**：清单、pending、失败列表都写到本地文件，脚本中断/重启不丢进度

## 经验教训

1. **掉盘的报错信息会骗人**。CDFS 掉盘时报 `Permission denied` 而不是 I/O error，差点导致误判放弃数据。任何"永久失败"判定前，必须确认设备本身是否还活着。

2. **物理设备的问题，软件层能做的有限但并非没有**。`No Media` 是主控自己报告的，Windows 再怎么折腾也没用；但抓住"冷态正常窗口"这个物理特性，软件就能把数据抢出来。

3. **批量抢救脚本的核心是"失败语义"**：什么算掉盘、什么算永久失败、什么算可重试 —— 分清楚这三者的脚本才能稳健地反复横跳于窗口之间。

4. **量产工具必须精确匹配主控**。PS3281B 这类代工主控（`VID_346D` 是通用 VID，Intenso/Philips/Kingston 都在用），量产工具选错直接变砖。量产前必须用 ChipGenius 确认主控型号和 Flash 型号。

## 遗留问题

- U 盘本体是 **NAND 虚焊**，虽然数据抢出来了，但盘本身随时可能再掉 —— 建议拆壳补焊或换新
- 如果想去掉虚拟光驱、把 U 盘量产成纯存储盘（可扩容约 4.76GB），需要走量产流程，但虚焊状态下量产中途掉盘 = 主控变砖，风险很高，**建议先补焊再量产**
