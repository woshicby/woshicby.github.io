# 一台新服务器从零到 vLLM 推理的完整记录

最近入手了一台全新的 AI 推理服务器：双路 Xeon Gold（128 线程）、256GB DDR5、2×1.92TB SSD（RAID1 系统盘）+ 4×8TB HDD（RAID5 数据盘）、4× NVIDIA RTX PRO 5000 72GB Blackwell、双口千兆网卡、4×2700W 冗余电源。目标是跑全量 DeepSeek-V4-Flash 推理。这篇文章完整记录从拆箱到跑通的整个过程——尤其是 Blackwell (SM120) 新架构给 vLLM 部署带来的连环坑。

## 一、发现设备：局域网多了一台 Linux

新服务器接进局域网后，第一件事是确认它上线了。用 ARP 级扫描（比 ICMP ping 可靠，能发现屏蔽 ping 的设备）扫出网段内所有在线设备，逐一对照：路由器、NAS、笔记本……然后锁定了一台不认识的主机。

扫描它的开放端口，看到 SSH + lighttpd(80/443) + VNC(5900)，SSH banner 显示 Debian 系系统。443 上的 Web 界面标题是 "Server Mgmt"——顺着 JS 资源里的 `MEGARAC SPX` 字符串，确认这是 **AMI MegaRAC BMC**（服务器带外管理控制器）。Redfish 服务返回了 `Product: X640G50`——技嘉的 AMD EPYC 平台服务器，与序列号对应的 MAC 也对上了。

> 小知识：现代服务器主机系统和 BMC 是两个独立系统、两个独立网口。SSH 到"22 端口"可能进的是 BMC 的 SSH，不是主机系统的——BMC 固件本身也基于 Debian。所以后来发现"系统明明是 Ubuntu 24.04，SSH banner 却是 Debian 10"一点都不矛盾：22 端口是 BMC 的，主机系统 SSH 根本没占这个端口。

## 二、硬件核查：不拆机验配置单

新机第一关是验证配置单是否属实。全程只用静态查询命令，**零负载**（办公室环境，风扇不能起飞）：

- CPU：`lscpu` 确认 2 路 × 32 核 128 线程
- 内存：`dmidecode` 确认 4 条 64GB DDR5
- RAID 卡：`lspci` 看到 LSI 3108（即 9361-8i），`dmesg` 显示 `MR(2048MB)` 确认 2GB 缓存
- 磁盘：装 `smartctl` 逐块读物理盘型号（2×SE005-1920GB SSD + 4×HGST 8TB）
- 卷布局：装 **storcli**（LSI 官方工具）一锤定音——VD0=RAID1(2×SSD) 系统盘、VD1=RAID5(4×HDD) 21.8TB 数据盘
- GPU：`nvidia-smi` 4 张 RTX PRO 5000 72GB Blackwell 全识别
- 电源：`ipmitool sensor` 看到 4 个 PSU 在位（主供电 + 冗余）

全程风扇稳定在 4000 RPM 左右，没起飞。

## 三、系统部署：数据盘与 SSH

主机 Ubuntu 24.04.3 只有命令行。业务网口接上后 DHCP 拿到地址，SSH 服务装好并设置开机自启。21.8TB RAID5 阵列分一个 GPT 分区格式化成 ext4，挂载到 `/data`，UUID 写进 fstab——重启自动挂载。

顺便把 HuggingFace 模型缓存目录重定向到数据盘（`HF_HOME=/data/hf`），模型都往大容量盘放。

## 四、BMC 密码之谜：从 IPMI 里"造"一个管理员

新 BMC 默认密码试了一轮常见组合全部失败。用主机侧的 IPMI 本地通道（`/dev/ipmi0`，主机 root 直接访问 BMC，不需要 BMC 密码）排查，发现 BMC **出厂未初始化**——只有一个空名固定用户，从来没有配置过管理员。

解法：直接用 `ipmitool user set password` 给 BMC 的 admin 用户设置密码，再赋管理员权限。一台从未初始化过的 BMC 就这样有了可登录的 Web 管理员。

## 五、vLLM 部署：Blackwell (SM120) 的连环坑

这是整篇文章的重头戏。4×72GB 跑 149GB FP8 模型，理论上 TP=4 每卡 ~37GB 权重，完全放得下。但启动过程踩遍了新架构的坑：

### 坑 1：FP8 模型要求 FP8 KV cache

```
AssertionError: DeepseekV4 fp8_ds_mla layout only supports fp8 kv-cache, got auto
```

DeepSeek-V4-Flash 是 FP8 量化模型，它的 MLA 注意力布局强制要求 KV cache 也是 FP8。解法：启动参数加 `--kv-cache-dtype fp8`。

### 坑 2：服务器没有 CUDA toolkit（nvcc）

```
Module vllm.third_party.deep_gemm was found but failed to import
assert cuda_home is not None
```

vLLM 的 FlashInfer 和 DeepGEMM 都需要 nvcc 做 JIT 编译，但服务器只装了显卡驱动、没有 CUDA toolkit。最轻量的解法是 pip 装 `nvidia-cuda-nvcc-cu13`（只装 nvcc，不装整套 CUDA）。

### 坑 3：缺 g++、缺 Python 头文件、缺 ninja

装完 nvcc 后编译继续报错，一路补齐：

- `g++ / build-essential`——nvcc 编译宿主代码需要 cc1plus
- `python3.12-dev`——Triton 编译需要 Python.h
- `ninja-build`——torch.compile 的构建工具

### 坑 4：CUDA 组件版本不匹配

```
error: "CUDA compiler and CUDA toolkit headers are incompatible"
```

nvcc 是 13.3，但 pip 装的 `nvidia-cuda-runtime` 还是 13.0——头文件版本检查失败。解法：升级 runtime 到 13.3 对齐，并把 `CUDA_HOME` 指向 pip 的 cu13 目录、`LD_LIBRARY_PATH` 加上它的 lib。

### 坑 5：FlashInfer SM120 特化缺失

```
FLASHINFER_MLA_SPARSE_DSV4 on SM120 requires a FlashInfer DSV4 sparse MLA decode specialization
```

RTX PRO 5000 是 **compute capability 12.0 (SM120)**，FlashInfer 旧版本没有 SM120 的稀疏 MLA kernel。升级 `flashinfer-python` 到包含该特化的版本解决。（它的 dispatch 表里 `(16, 128)` 正是 DeepSeek V4 需要的配置。）

### 坑 6：JIT 链接找不到 libcudart

```
/usr/bin/ld: cannot find -lcudart
```

FlashInfer JIT 编译链接时在 `cu13/lib64` 找 `libcudart`，但 pip 包把它放在 `cu13/lib/libcudart.so.13`。建符号链接解决：

```bash
mkdir -p .../nvidia/cu13/lib64/stubs
ln -sf ../lib/libcudart.so.13 .../cu13/lib64/libcudart.so
ln -sf /usr/lib/.../libcuda.so.1 .../cu13/lib64/stubs/libcuda.so
```

### 坑 7：模型权重文件损坏

所有环境问题解决后，权重加载到 83% 报 `SafetensorError: invalid JSON in header`——**本地源文件的 3 个 safetensors 分片在下载时就损坏了**（文件大小正常但 header 是坏的）。用 Python 遍历验证所有 46 个分片定位损坏文件，从 HF 镜像重新下载这 3 个分片修复。

### 坑 8：CUDA graph 捕获 OOM——显存账

```
CUDA out of memory. Tried to allocate 120.00 MiB. GPU 0 has a total capacity of 71.12 GiB of which 80.31 MiB is free.
```

首次启动时 CUDA graph 捕获阶段 OOM。这暴露了张量并行下的显存本质：**TP=4 时每张卡独立使用自己的 72GB，不是 288GB 共享池**。每卡账本：

| 占用 | 大小 |
|---|---|
| 模型权重（149G ÷ 4） | ~37 GiB |
| KV cache pool（0.9 util） | ~22.4 GiB |
| 激活 + workspace | ~11 GiB |
| **合计** | **~71 GiB = 单卡上限** |

CUDA graph 捕获峰值需要额外 ~12GB（51 个 batch size 的 graph 各占私有池），物理空间不够就 OOM。试过降 max-model-len 腾空间、减 graph 数量，最终在"速度 vs 稳定性"上选择了 **eager 模式**（`--enforce-eager` 跳过 graph 捕获）：牺牲一点速度，换来 0.9 util 下 22.4GB KV cache 的稳定运行。

## 六、性能基准（eager 模式）

固定 512 token 输入 / 256 token 输出，串行 20 请求：

- 输出吞吐：~85 tok/s
- 总吞吐（含输入）：~256 tok/s
- 平均首 token 延迟（TTFT）：~10s
- 每 token 生成时间（TPOT）：~135ms

CUDA graph 若能用，decode 速度理论上能提升 1.5~3 倍——这是后续调优方向（SM120 的 graph 捕获需要更精细的显存预算管理）。

## 七、接入 Hermes

Hermes Agent 支持自定义 OpenAI 兼容 provider，配置命名 provider 指向 vLLM 即可：

```yaml
providers:
  vllm:
    api: http://<服务器地址>:8000/v1
    api_key: ''
    discover_models: true
```

一个额外坑：Hermes 是 agent，请求带 `tool_choice: auto`，vLLM 必须加 `--enable-auto-tool-choice --tool-call-parser hermes` 才能接受。

## 八、经验总结

1. **新服务器先分清 BMC 和主机系统**——两个系统、两个网口、两套凭据
2. **硬件核查零负载可完成**——lscpu/dmidecode/lspci/smartctl/storcli/ipmitool 全是静态查询
3. **SM120 新架构 = 所有 CUDA 组件都要新版对齐**——nvcc、runtime、cccl、FlashInfer 一个都不能旧
4. **pip 分散式 CUDA 组件是版本雷区**——nvcc 13.3 配 runtime 13.0 就会炸，记得 `CUDA_HOME` + `LD_LIBRARY_PATH` 一起指对
5. **TP 显存按单卡算**——总显存除以卡数才是每个 worker 的实际池子
6. **模型文件下载后要验证**——safetensors header 可快速遍历检查，别等加载到 83% 才发现
7. **agent 框架接 vLLM 要开工具调用**——`--enable-auto-tool-choice` 别忘了

最终这台机器以 eager 模式稳定运行全量 DeepSeek-V4-Flash（4 卡 TP、FP8 KV cache、22.4GB KV），接入 Hermes 直接可用。等有空再战 CUDA graph 的显存预算优化。
